# StudyMate

StudyMate — платформа для студентов: профиль с компетенциями, поиск учебных проектов, отклики на роли, подбор команды и вопросы руководителю. Студент может одновременно быть участником одного проекта и руководителем другого.

## Текущее состояние

Подготовлены только `requirements.txt`, `AGENTS.md` и этот README. Приложения, `manage.py`, моделей, миграций, тестов, Dockerfile, `compose.yaml` и `.env.example` пока нет. Установка зависимостей доступна сейчас; команды запуска приложения ниже — контракт для будущей реализации, а не утверждение, что проект уже запускается. Реализация требует отдельной задачи.

Ведение `requirements.txt`, `AGENTS.md` и `README.md` — ответственность техлида. Изменения зависимостей, стека, обязательных проверок, команд запуска и правил работы нужно заранее согласовать с ним. Разработчики и их агенты передают предложения техлиду, сохраняя согласованные настройки проекта.

## Рекомендации по архитектуре

Начать с Django-монолита: сервер формирует страницы и HTML-фрагменты, HTMX отвечает за поиск, фильтры, модальные формы и обновление статусов. Для проверки Python-кода использовать Ruff, для автоматизированных тестов — pytest. Все тесты и фикстуры хранить в корневой папке `tests/`. Дополнительный API, SPA, Redis и очередь задач из текущих сценариев не следуют.

Предлагаемые границы приложений, которые команда должна закрепить до создания каркаса:

| Модуль | Ответственность |
| --- | --- |
| `accounts` | Email-вход, профиль, навыки студента, аватар |
| `projects` | Карточка, каталог, роли, компетенции, этапы и статусы |
| `applications` | Заявки, членство, занятые места, сопоставление навыков |
| `questions` | Вопросы, ответы, ограничения и видимость |
| `notifications` | Уведомления, прочтение, счётчики и сводка |

Справочники навыков и направлений должны иметь единого владельца и единую модель. Общий `config` содержит настройки и корневую маршрутизацию. Многошаговые бизнес-операции оформлять сервисными функциями; запросы для каталогов и карточек держать отдельно от шаблонов. Не дробить проект на микросервисы и не добавлять абстракции без практической потребности.

### Что согласовать по данным до первых миграций

Это выявленные расхождения и предложения, а не уже утверждённые изменения БД.

| Вопрос | Что обнаружено | Рекомендация / необходимое решение |
| --- | --- | --- |
| Авторизация | БД содержит собственные sessions, reset tokens, password_hash и OAuth XOR password; для входа нужны email/пароль | Кастомный Django User с UUID и email-входом до первой миграции; стандартные пароли и сессии Django. Согласовать отображение схемы и границы OAuth/reset |
| ФИО | `full_name NOT NULL`, но регистрация содержит только email и пароль | Определить допустимое незаполненное значение и момент обязательного заполнения |
| Email/пароль | UNIQUE email не определяет регистронезависимость; для пароля задан минимум 6 символов | Согласовать нормализацию и уникальность email в БД. Рекомендую повысить минимум пароля до 8, но не менять требование 6 без решения владельца |
| Профиль | В БД нет вуза, специальности, курса, желаемой роли, интересов | Согласовать поля/модель профиля; навыки отделить от интересов; уточнить обязательность ФИО и типы навыков |
| Проект | Нет сложности и этапов; title допускает 255 вместо планируемых 3–100; category nullable при обязательном направлении | Согласовать поля и ограничения: описание ≤5000, минимум одна роль, требуемые навыки. Уточнить значение «дедлайн»: окончание проекта или срок откликов |
| Роль в заявке | `applications` не содержит role_id; в членстве роль хранится текстом | Нужна связь заявки/членства с project_roles и проверка принадлежности роли проекту; сохранять историческое название удалённой роли |
| Места | БД использует count, в логике мест нужны вместимость и занятость; max_members=10 при планируемых 1–20 местах на роль | Единое имя вместимости; занятость считать по членству. Уточнить общий лимит и входит ли руководитель в число мест |
| Отзыв и повторная подача | Нужно определить, занимает ли pending место или оно занято только после принятия; нет withdrawn, UNIQUE запрещает повторную заявку | Рекомендую занимать место только после принятия. Решить историю отзыва и повторную подачу после отзыва/отказа/исключения, затем выбрать статусы и ограничения |
| Закрытие набора | БД смешивает этап и набор в status; нужно определить получателей уведомления «Отклонено» | Уточнить переходы open/in_progress/completed/cancelled и закрытие роли. Рекомендую отклонять только pending, сохраняя участников; косметические изменения не меняют статусы заявок |
| Удаление проекта | Нужна история заявки «Проект удалён»; нет soft delete проекта; завершённый проект должен сохраняться | Согласовать soft delete/снимок истории и on_delete; не уничтожать историю каскадом; сохранить запрет удаления completed |
| Причина отказа | В БД нет причины отклонения | Добавить согласованное поле причины, источник решения и время рассмотрения |
| Параллельное редактирование | Нужно предупреждение об изменении в другой вкладке | Версия записи или атомарная проверка updated_at; защита от потери обновлений |
| Соответствие навыков | Не определён уровень требований — проект или роль; в БД навыки только проекта | Уточнить уровень требований, округление и нулевой знаменатель; считать уникальные навыки, не учитывать уровни навыков без отдельного требования |
| Вопросы | БД допускает дерево comments, для интерфейса нужны вопрос и ответ руководителя | Ограничить глубину и авторство; решить число ответов, хранение прочтения, входят ли удалённые вопросы в лимит 5 |
| Уведомления | Есть type/content/is_read; для ежедневной сводки нужны дополнительные правила | Согласовать связь с событием, защиту от дублей, время и порог сводки. Предлагаю management command + внешний планировщик; Celery обсуждать при росте нагрузки |
| Публичность | Каталог требует входа, вопросы публичны; внешний профиль показывает active/completed, pending упоминается в «Моих проектах» | Матрица доступов; собственные заявки отделить от публичного портфолио |
| Дополнительные функции | Есть invitations, attachments, OAuth и просмотры, но границы этих функций ещё не определены | Не включать в MVP автоматически. Для анонимных просмотров UNIQUE(project_id,user_id) не устраняет дубли NULL — определить метрику и срок хранения IP |

UUID можно создавать через `uuid.uuid4` без uuid-ossp; отклонение от `uuid_generate_v4()` нужно согласовать. Для связующих таблиц предложены обычный PK и UniqueConstraint на пару вместо составного PK: так проще стандартным Django relations/admin. Физическую схему утвердить до генерации миграций.

### Транзакции, безопасность и поиск

Принятие заявки должно в одной транзакции проверить автора, статусы проекта/заявки, заблокировать общую строку роли/проекта, повторно проверить вместимость, добавить членство и изменить статус. Закрытие набора, удаление роли, исключение и редактирование мест используют совместимый порядок блокировок. Повтор запроса не создаёт второго участника или уведомления. Последовательность кликов в интерфейсе не исключает гонки на сервере.

Проверки доступа нужны для каждого объекта, включая HTMX. Для изменений — POST и CSRF. Пользовательский текст экранировать; длины и бизнес-ограничения проверять сервером. Аватары проверять Pillow по содержимому, размеру файла и числу пикселей; лимиты и форматы согласовать до реализации.

Поиск начать с регистронезависимого поиска по названию/описанию, соответствующего примеру «чат» → «чат-бот». Полнотекстовый поиск PostgreSQL не равнозначен подстроке. При росте данных измерить запросы и обсудить pg_trgm/GIN, не подключать Elasticsearch заранее. Предусмотреть пагинацию, select_related/prefetch_related и индексы под реальные фильтры.

### Порядок разработки

1. Согласовать с техлидом спорные пункты, MVP, права и переходы статусов. Зафиксировать решения в задаче; ключевые договорённости техлид отражает в документации.
2. Один владелец создаёт каркас, кастомного пользователя, окружение, Docker, игнорирование секретов и первичные миграции. Проверяет пустую PostgreSQL БД.
3. После закрепления контрактов разделить профиль, каталог, заявки и вопросы между разработчиками. Каждую фичу и каждый баг выполнять исключительно в отдельной ветке (`feature/<имя>` или `fix/<имя>`) с последующим PR и ревью. Эти же правила действуют для агентов, используемых разработчиками. Изменения общих файлов и миграций координировать по AGENTS.md.
4. Реализовать путь: регистрация → профиль → публикация → отклик → принятие → уведомление. Затем крайние случаи, управление командой, вопросы и суточная сводка.
5. Добавить CI с PostgreSQL и командами ниже: Ruff, проверки миграций, pytest и обзор каждого PR. Точные версии инструментов и конфигурацию закрепляет техлид; новые инструменты согласовывать с ним.

## Подготовка окружения сейчас

Все команды выполняются из корня репозитория `study-mate` — папки с README.md и requirements.txt. Откройте терминал в этой папке своей локальной копии. На Windows нужен CPython 3.13.16 x64. Docker Desktop с Linux containers и Compose v2 понадобится для запуска БД. Зависимости устанавливать в виртуальное окружение.

PowerShell:

```powershell
py -3.13 --version
py -3.13 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m pip check
.\.venv\Scripts\python.exe -c "import django, psycopg, PIL; print(django.get_version(), psycopg.__version__, PIL.__version__)"
```

Ожидаемые версии: `5.2.17 3.3.6 13.0.0`; pip check должен завершиться без конфликтов. Прямой вызов Python не требует изменения ExecutionPolicy. Если активация разрешена, можно выполнить `.\.venv\Scripts\Activate.ps1`, после чего использовать `python -m pip install -r requirements.txt`.

Linux/macOS (при установленном Python 3.13.16):

```bash
python3.13 --version
python3.13 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python -m pip check
python -c "import django, psycopg, PIL; print(django.get_version(), psycopg.__version__, PIL.__version__)"
```

Использовать именно `python -m pip install -r requirements.txt`: ключ `-r` обязателен. Не обновлять зависимости массовым upgrade и не заменять manifest выводом pip freeze из постороннего окружения.

## Контракт будущего запуска

**Следующие команды заработают только после отдельной реализации каркаса.** Её исполнитель должен создать manage.py в корне, Dockerfile, compose.yaml, `.env.example`, `.gitignore`, `.dockerignore` и настройки Django, реально выполнить инструкцию и передать техлиду необходимые уточнения README. Перед началом реализации техлид также закрепляет версии разрешённых Ruff и pytest в зависимостях разработки и настраивает запуск Django-тестов через pytest. Сейчас эти инструменты в requirements.txt ещё не включены.

Compose предоставляет сервисы `db` и `web`: PostgreSQL с healthcheck через pg_isready и именованным volume; web с ожиданием healthy db, установкой requirements и dev-сервером на `0.0.0.0:8000` внутри контейнера. Публикация портов только на `127.0.0.1`. Dockerfile фиксирует Python 3.13.16 и проверенный digest. Пароли и SECRET_KEY не включаются в образ. Миграции выполняются явной командой одним исполнителем, не каждым контейнером параллельно.

| Переменная | Значение для разработки / смысл |
| --- | --- |
| DJANGO_SECRET_KEY | Случайное локальное значение; обязательно, без встроенного секрета |
| DJANGO_DEBUG | `1` для разработки, явный разбор boolean |
| DJANGO_ALLOWED_HOSTS | `localhost,127.0.0.1`, явный разбор списка |
| POSTGRES_DB | `studymate` |
| POSTGRES_USER | `studymate` |
| POSTGRES_PASSWORD | Собственный локальный пароль |
| DB_HOST | `127.0.0.1` для локального Python, `db` внутри web |
| DB_PORT | `5432` внутри сети Compose |
| POSTGRES_PORT | `5432` снаружи; при конфликте можно `5433` |

Compose должен публиковать БД как `127.0.0.1:${POSTGRES_PORT:-5432}:5432`, передавать POSTGRES-переменные обоим сервисам, а web явно задавать DB_HOST=db и DB_PORT=5432. Каждый разработчик запускает собственное локальное окружение с отдельными данными и секретами. Не задавать глобальный container_name или фиксированное глобальное имя volume.

### Вариант A — всё в Docker

После появления перечисленных файлов, в PowerShell:

```powershell
Copy-Item .env.example .env
```

Заполнить `.env` локальными значениями и секретами. Копировать только при первом запуске: не перезаписывать существующий файл. Compose читает `.env` для подстановок, но передача переменных контейнеру должна быть настроена явно через environment/env_file.

```powershell
docker version
docker compose version
docker compose config --quiet
docker compose build
docker compose up -d --wait db
docker compose run --rm web python manage.py migrate --noinput
docker compose run --rm web python manage.py check
docker compose run --rm web python manage.py createsuperuser
docker compose up -d web
docker compose ps
docker compose logs --tail=100 web
```

Открыть [локальный сайт](http://127.0.0.1:8000/). В реализации корневой URL должен отдавать страницу входа/каталог либо корректный редирект. Суперпользователь создаётся один раз; обычные сценарии проверять отдельными аккаунтами.

### Вариант B — Python локально, PostgreSQL в Docker

Подготовить окружение и `.env` как выше. В текущем PowerShell экспортировать **те же** данные подключения. Django сам по себе `.env` не читает; библиотека dotenv не добавлена:

```powershell
$env:DJANGO_SECRET_KEY = & .\.venv\Scripts\python.exe -c "import secrets; print(secrets.token_urlsafe(64))"
$env:DJANGO_DEBUG = '1'
$env:DJANGO_ALLOWED_HOSTS = 'localhost,127.0.0.1'
$env:POSTGRES_DB = 'studymate'
$env:POSTGRES_USER = 'studymate'
$env:POSTGRES_PASSWORD = Read-Host 'Локальный пароль PostgreSQL из .env'
$env:DB_HOST = '127.0.0.1'
$env:DB_PORT = '5432'
docker compose config --quiet
docker compose up -d --wait db
.\.venv\Scripts\python.exe manage.py migrate --noinput
.\.venv\Scripts\python.exe manage.py check
.\.venv\Scripts\python.exe manage.py createsuperuser
.\.venv\Scripts\python.exe manage.py runserver 127.0.0.1:8000
```

При другом POSTGRES_PORT установить его в локальный DB_PORT. Linux/macOS используют аналогичные `export NAME=value` и python из активированной .venv. Не запускать локальный сервер и web-контейнер на одном порту. Runserver предназначен для разработки; production-сервер, HTTPS, static/media и резервное копирование выбираются отдельной задачей.

## Проверка перед интеграцией

На текущем этапе: сверить требования, версии, синтаксис manifest и `git diff --check`. Проверка приложения недоступна до реализации.

Для каждой фичи и исправления бага обязателен `ruff check`. Это статическая проверка, поэтому изменённый сценарий также проверяется вручную. По возможности добавить pytest-тесты; если их нет, объяснить причину и ручную проверку в PR. Существующие релевантные тесты должны проходить, а перед интеграцией запускается весь существующий набор. Тесты, фикстуры и conftest.py размещаются только в корневой папке `tests/`, например `tests/accounts/test_profile.py`.

После реализации каркаса и настройки инструментов техлидом, для варианта A (dev-образ должен содержать Ruff и pytest):

```powershell
docker compose run --rm web python -m pip check
docker compose run --rm web python -m ruff check .
docker compose run --rm web python manage.py check
docker compose run --rm web python manage.py makemigrations --check --dry-run
docker compose run --rm web python manage.py migrate --check
docker compose run --rm web python -m pytest tests
git diff --check
```

Для варианта B:

```powershell
.\.venv\Scripts\python.exe -m pip check
.\.venv\Scripts\python.exe -m ruff check .
.\.venv\Scripts\python.exe manage.py check
.\.venv\Scripts\python.exe manage.py makemigrations --check --dry-run
.\.venv\Scripts\python.exe manage.py migrate --check
.\.venv\Scripts\python.exe -m pytest tests
git diff --check
```

Все применимые команды должны завершиться с кодом 0; новые миграции не требуются, существующие применены. До появления тестов запуск pytest отмечать как неприменимый: отсутствие собранных тестов не подтверждает работоспособность. Для Django-тестов техлид настраивает инициализацию Django и отдельную тестовую БД PostgreSQL, например `test_studymate`; при её автоматическом создании нужен пользователь с соответствующим правом. Использовать локальный/CI PostgreSQL, никогда production. Каждый разработчик использует собственную БД. Новые миграции проверять на пустой БД и на предыдущей схеме с тестовыми данными.

| Каталог | Поиск от 3 символов без учёта регистра; AND между категориями / OR внутри; сброс, пустая выдача, пагинация, сохранение URL и Back |

| Создание и редактирование проекта | Название 3–100, описание ≤5000, роли/места, дедлайн; повтор названия у автора; чужое редактирование; устаревшая версия; запрет удаления completed |
| Вопросы и ответы | Вопрос 15–500, максимум 5; ответ 3–1000 только руководителем; удаление собственного вопроса лишь без ответа; удаление ответа; анонимная видимость; суточная сводка |
| Подбор и управление командой | Совпадение навыков и пересчёт, сортировки; приём/отказ; исключение освобождает место; запрет удаления занятой роли и вместимости ниже занятости; повторный набор |

Обязательные интеграционные проверки: два кандидата одновременно принимаются на последнее место; приём одновременно с закрытием набора/изменением вместимости; повтор POST не дублирует данные; чужой пользователь отправляет прямой POST/HTMX; CSRF без токена отклоняется; полная страница и HTMX-фрагмент корректны; ошибка формы не стирает ввод. Тесты блокировок запускать через pytest с отдельными соединениями PostgreSQL и настройкой реальных транзакций. В браузере проверить фокус модального окна, клавиатуру, ошибки и истёкшую сессию.

Отчёт в PR: задача, коммит/ветка, среда, команды, результат Ruff, число pytest-тестов, ручные сценарии и ограничения. Если тесты не добавлены, указать причину. CI и локальная проверка используют одинаковые команды. Один manage.py check или Ruff не подтверждает работоспособность всего проекта.

## Остановка и типовые проблемы

```powershell
docker compose logs --tail=100 db web
docker compose stop
```

Stop сохраняет контейнеры и данные. Down удаляет контейнеры и сеть, но сохраняет обычный именованный volume. Не применять `down -v`, prune или удаление volume без явного решения об уничтожении данных.

- Нет manage.py/compose.yaml: каркас ещё не создан, будущая инструкция пока неприменима.
- Нет py -3.13: установить согласованный CPython и проверить `py -0p`; не подменять версию молча.
- Docker daemon недоступен: запустить Docker Desktop и проверить Linux containers.
- Порт занят: выбрать другой POSTGRES_PORT и соответствующий локальный DB_PORT.
- БД недоступна: проверить healthy, host (`db` внутри Compose, localhost снаружи), порт и credentials. Изменение пароля в .env не меняет пароль уже инициализированного volume.
- Тесты не создают БД: проверить локальные права CREATEDB и отсутствие конкурирующего процесса на той же тестовой БД.
- Пакет не устанавливается: проверить Python, платформу, доступ к PyPI и конкретную ошибку. Не снимать pin и не менять драйвер без обсуждения.

## Дополнительные инструменты

Разрешены Psycopg, Pillow, Ruff и pytest. Ruff обязателен для проверки каждой фичи и исправления бага; pytest используется для автоматизированных тестов в `tests/`. Версии инструментов и изменения requirements.txt закрепляет техлид. Интеграцию pytest с Django, в том числе необходимость pytest-django, определяет техлид при настройке каркаса. Django-htmx — необязательная обёртка: HX-Request можно читать напрямую. Pre-commit и другие новые инструменты согласовываются отдельно. Celery/Redis/Channels нужны только при подтверждённой потребности в очередях или реальном времени. OAuth-библиотеку, production WSGI/ASGI-сервер и хранилище медиа выбирать после уточнения соответствующих требований.
