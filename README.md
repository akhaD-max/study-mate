# StudyMate

StudyMate — платформа для поиска учебных проектов и формирования студенческих команд. Студент может одновременно быть участником одного проекта и руководителем другого.

## Текущее состояние

Реализованы регистрация и вход по email, выход, каталог с поиском, фильтрами и сортировкой, карточка и создание проекта, разделы «Мои проекты» и «Мои заявки». Студент выбирает доступную роль и подаёт заявку; руководитель просматривает входящие заявки, принимает или отклоняет их. Заявку на рассмотрении можно отозвать, участник может выйти из проекта.

В проекте есть кастомный пользователь с UUID, модели проектов, ролей, участников и заявок, начальные миграции, Django admin, команда демо-данных и автоматизированные тесты в `tests/`. Интерфейс построен на Django templates и локальном HTMX. Django и PostgreSQL запускаются через Docker Compose; данные БД сохраняются в именованном volume.

Профиль с компетенциями, вопросы и ответы, уведомления, подбор по навыкам и полноценное редактирование проекта пока не реализованы.

Ведение `requirements.txt`, `AGENTS.md` и `README.md` — ответственность техлида. Изменения зависимостей, стека, обязательных проверок, команд запуска и правил работы нужно заранее согласовать с ним. Разработчики и их агенты передают предложения техлиду, сохраняя согласованные настройки проекта.

## Стек и точные версии

Версии сверены с официальными страницами и метаданными PyPI 18.10.2026. Это выбранная база проекта; обновления безопасности нужно регулярно проверять и вносить отдельным проверяемым изменением.

| Компонент | Версия | Назначение |
| --- | --- | --- |
| CPython | 3.13.16 | Единая версия; в Docker входит в образ, для локального Python устанавливается отдельно |
| Django | 5.2.17 LTS | ORM, формы, шаблоны, auth, sessions, admin и тесты |
| PostgreSQL | 17.11 | Основная и тестовая БД; сервис `db` на образе `postgres:17.11-bookworm` |
| HTMX | 2.0.11 | HTML-фрагменты; JavaScript, не pip-пакет |
| psycopg[binary] | 3.3.6 | Драйвер PostgreSQL; согласован владельцем |
| Pillow | 13.0.0 | Проверка и обработка аватаров; согласован владельцем |
| asgiref | 3.12.1 | Транзитивная зависимость Django |
| sqlparse | 0.6.0 | Транзитивная зависимость Django |
| psycopg-binary | 3.3.6 | Бинарная реализация extra `binary` |
| tzdata | 2026.5 | Данные часовых поясов для Windows |

Все Python-пакеты фиксируются в requirements.txt с `==`. Manifest рассчитан на CPython 3.13, где Psycopg не требует typing-extensions. Это фиксация версий, не lock-файл с хешами и не доказательство успешной сборки на всех платформах. Для CI проверить установку на Windows и Linux. Базовые Docker-образы уже закреплены по версии и digest; при обновлении сохранять эту фиксацию. Не использовать `latest`.

Django 5.2 выбран как LTS с поддержкой до апреля 2028. PostgreSQL 17 совместим с Django 5.2. HTMX хранится локально в `static/vendor/` вместе с лицензией и сведениями об источнике и контрольной сумме, чтобы запуск не зависел от CDN. Node.js и npm для этого не нужны.

Источники: [Django](https://www.djangoproject.com/download/), [совместимость Python](https://docs.djangoproject.com/en/5.2/releases/5.2/), [PostgreSQL backend](https://docs.djangoproject.com/en/5.2/ref/databases/), [Python](https://www.python.org/downloads/), [PostgreSQL](https://www.postgresql.org/support/versioning/), [HTMX](https://htmx.org/docs/), [Psycopg](https://pypi.org/project/psycopg/3.3.6/), [Pillow](https://pypi.org/project/Pillow/13.0.0/), [asgiref](https://pypi.org/project/asgiref/3.12.1/), [sqlparse](https://pypi.org/project/sqlparse/0.6.0/), [tzdata](https://pypi.org/project/tzdata/2026.5/).

## Клонирование

Откройте Powershell / терминал в папке, куда хотите скачать проект, и введите:

```powershell
git clone https://github.com/akhaD-max/study-mate.git
cd study-mate
```

## Первый запуск через Docker

Перед запуском откройте Docker Desktop в режиме Linux containers.
Далее соберите окружение проекта:

```powershell
docker compose build
```

При сборке Docker загрузит базовые образы Python 3.13.16 и PostgreSQL 17.11
и установит точные версии библиотек из requirements.txt.
Создайте локальный файл настроек .env со случайными секретами:

```powershell
docker compose run --rm --no-deps --user 0 --volume "${PWD}:/workspace" --workdir /workspace web python scripts/setup_env.py
```

Запустите БД, примените существующие миграции и затем запустите приложение:

```powershell
docker compose up -d --wait db
docker compose run --rm web python manage.py migrate
docker compose up -d --wait web
```

Откройте [StudyMate](http://localhost:8000/).
Если порт занят, измените WEB_PORT в файле .env, например
на 8001, и повторите команду запуска. Тогда адрес будет
http://localhost:8001/.

### Миграции и данные приложения

Кастомный пользователь `accounts.User` уже подключён, начальные миграции входят в репозиторий. Применение миграций включено в основной путь запуска выше. Моделями и созданием новых миграций управляет Денис; миграции для каждой БД выполняются явно, одним исполнителем.

Если ранее уже применены миграции стандартного пользователя Django, согласуйте переход с Денисом, сохранив существующие данные.

### Демо-данные

После миграций можно загрузить примеры для локальной проверки. Замените значение пароля своим (минимум 6 символов):

```powershell
docker compose run --rm web python manage.py seed_demo --password "LocalDemo-ChangeMe"
```

Команда создаёт три направления, 14 проектов, свободные, занятые и закрытые роли, участников и заявки со статусами «На рассмотрении», «Принята» и «Отклонена». В исходном наборе 13 проектов с доступным набором — достаточно для двух страниц каталога. Примеры поиска и ожидаемые результаты приведены в [описании демо-данных](docs/sprint6/demo-search-data.md).

| Email | Назначение |
| --- | --- |
| `author@studymate.local` | Руководитель демо-проектов, просмотр и рассмотрение входящих заявок |
| `student1@studymate.local` | Студент с примерами заявок во всех трёх статусах |
| `student2@studymate.local` | Студент с участием в проекте и заявкой на рассмотрении |

У всех трёх пользователей пароль из команды. Для новой заявки войдите первым студентом и выберите свободную Backend-роль в проекте «Платформа учебных команд StudyMate». Демо-пользователи не получают доступ в admin.

Повторный запуск не создаёт дубли исходных примеров и не сбрасывает существующие заявки; пароли демо-пользователей обновляются на переданное значение. Команда дополняет данные, но не восстанавливает начальное состояние после всех ручных действий.

### Обновление и остановка

После изменения исходников пересоберите образ: текущий Compose копирует код при сборке и не подключает его через bind mount.

```powershell
docker compose build
docker compose up -d --wait db
docker compose run --rm web python manage.py migrate
docker compose up -d --wait web
```

Для остановки используйте `docker compose down`. Именованный volume PostgreSQL сохраняется; для обычного перезапуска не добавляйте `-v`.

Дополнительные сведения об окружении — в [docs/local-development.md](docs/local-development.md). Отчёты в `docs/` описывают состояние на момент их создания; актуальный порядок работы приведён здесь и в [AGENTS.md](AGENTS.md).

## Рекомендации по архитектуре

Используется Django-монолит: сервер формирует страницы и HTML-фрагменты, HTMX используется для интерактивных форм и обновления частей страницы. Для проверки Python-кода использовать Ruff, для автоматизированных тестов — pytest. Все тесты и фикстуры хранить в корневой папке `tests/`. Дополнительный API, SPA, Redis и очередь задач из текущих сценариев не следуют.

Существующие приложения и общие модули:

| Модуль | Ответственность |
| --- | --- |
| `accounts` | Кастомный пользователь, регистрация, email-вход, выход и проверка сессии |
| `main` | Перенаправление с главной в каталог и совместимость прежних ссылок |
| `projects` | Каталог, поиск и фильтры, создание и карточка проекта, «Мои проекты», направления, роли, членство и занятость мест, демо-данные |
| `applications` | Подача, просмотр и отзыв заявок, рассмотрение руководителем, принятие в команду и выход участника |
| `config` | Настройки Django, корневые URL, WSGI и ASGI |

Приложения `questions` и `notifications` пока не созданы. Их предполагаемая ответственность — вопросы и ответы руководителя, а также уведомления и сводки соответственно.

Справочники навыков и направлений должны иметь единого владельца и единую модель. Общий `config` содержит настройки и корневую маршрутизацию. Многошаговые бизнес-операции оформлять сервисными функциями; запросы для каталогов и карточек держать отдельно от шаблонов. Не дробить проект на микросервисы и не добавлять абстракции без практической потребности.

### Данные и бизнес-правила

- Пользователь — `accounts.User` с UUID и email-входом. Email приводится к нижнему регистру, уникальность без учёта регистра закреплена в БД. Пароли и сессии обрабатывает Django; минимальная длина пароля — 6 символов, также действуют стандартные проверки Django.
- При регистрации нужны email и пароль. `full_name` допускает пустую строку; редактор профиля пока отсутствует.
- Проект связан с автором и обязательным направлением. Создание проверяет название длиной 3–100 символов, непустое описание до 5000 символов и минимум одну роль. Вместимость роли в форме — 1–20 мест; название проекта уникально у автора.
- `ProjectRole` хранит вместимость и флаг `is_open`. Занятость считается по `ProjectMember`; заявка `pending` место не занимает. Автор проекта учитывается в отображаемом составе команды отдельно от участников по ролям.
- Заявка связана с пользователем, проектом и ролью. Сервис проверяет принадлежность роли проекту, открытый набор и свободные места. Автор и действующий участник не могут откликаться на свой проект; БД допускает только одну `pending`-заявку пользователя на проект независимо от роли.
- Статусы заявки: `pending`, `accepted`, `rejected`. Принятие создаёт членство, отказ меняет статус, отзыв удаляет только собственную `pending`-заявку. Отдельного статуса `withdrawn` и истории отзыва нет.
- У проекта есть статусы `open`, `in_progress`, `completed`, `cancelled`. Каталог определяет открытый набор по статусу `open` и наличию хотя бы одной открытой роли со свободным местом.
- Soft delete и сохранение истории после удаления проекта пока отсутствуют: связанные заявки удаляются каскадом. Поля профиля, навыки, сложность, дедлайн, этапы, причина отказа и уведомления требуют дальнейшего согласования и реализации.

### Транзакции, безопасность и поиск

Подача и рассмотрение заявок выполняются сервисными функциями в транзакциях. При принятии блокируются проект, роль и заявка в этом порядке, повторно проверяются права руководителя и доступность роли, создаётся членство и меняется статус. Повторное принятие уже принятой заявки не создаёт второго участника. При добавлении закрытия набора, удаления роли и редактирования мест нужно сохранять совместимый порядок блокировок.

Проверки доступа нужны для каждого объекта, включая HTMX. Для изменений — POST и CSRF. Пользовательский текст экранировать; длины и бизнес-ограничения проверять сервером. Аватары проверять Pillow по содержимому, размеру файла и числу пикселей; лимиты и форматы согласовать до реализации.

Поиск выполняется по подстроке в названии или описании без учёта регистра, например «чат» → «чат-бот». Каталог поддерживает одиночный выбор направления и роли, фильтр открытого набора, сортировку и пагинацию по 12 проектов. Условия применяются в БД до пагинации; связанные данные загружаются через select_related/prefetch_related. Полнотекстовый поиск PostgreSQL не равнозначен подстроке; дополнительные индексы стоит обсуждать после измерения запросов.

## Устройство локального окружения

Окружение описано в Dockerfile, compose.yaml, `.env.example` и настройках Django. Команды запуска приведены выше. Ruff и pytest пока не включены в requirements.txt и dev-образ; их версии и конфигурацию закрепляет техлид.

Compose предоставляет сервисы `db` и `web`: PostgreSQL с healthcheck через pg_isready и именованным volume; web с ожиданием healthy db, установкой requirements и dev-сервером на `0.0.0.0:8000` внутри контейнера. Публикация портов только на `127.0.0.1`. Dockerfile фиксирует Python 3.13.16 и проверенный digest. Пароли и SECRET_KEY не включаются в образ. Миграции выполняются явной командой одним исполнителем, не каждым контейнером параллельно.

| Переменная | Значение для разработки / смысл |
| --- | --- |
| DJANGO_SECRET_KEY | Случайное локальное значение; обязательно, без встроенного секрета |
| DJANGO_DEBUG | `1` для разработки, явный разбор boolean |
| DJANGO_ALLOWED_HOSTS | `localhost,127.0.0.1`, явный разбор списка |
| POSTGRES_DB | `studymate` |
| POSTGRES_USER | `studymate` |
| POSTGRES_PASSWORD | Собственный локальный пароль |
| DB_HOST | `127.0.0.1` для локального Python, `db` внутри web |
| DB_PORT | `5432` внутри сети Compose |
| POSTGRES_PORT | `5432` снаружи; при конфликте можно `5433` |
| WEB_PORT | `8000` снаружи; при конфликте можно `8001` |

Compose публикует БД как `127.0.0.1:${POSTGRES_PORT:-5432}:5432`, передаёт POSTGRES-переменные обоим сервисам, а web явно задаёт DB_HOST=db и DB_PORT=5432. Каждый разработчик запускает собственное локальное окружение с отдельными данными и секретами. Не задавать глобальный container_name или фиксированное глобальное имя volume.

## Проверка перед интеграцией

В `tests/` есть проверки авторизации, моделей, создания и поиска проектов, подачи и рассмотрения заявок и общего сценария. Для изменений только документации достаточно сверить команды, ссылки и выполнить `git diff --check`.

Для каждой фичи и исправления бага обязателен `ruff check`. Это статическая проверка, поэтому изменённый сценарий также проверяется вручную. По возможности добавить pytest-тесты; если их нет, объяснить причину и ручную проверку в PR. Существующие релевантные тесты должны проходить, а перед интеграцией запускается весь существующий набор. Тесты, фикстуры и conftest.py размещаются только в корневой папке `tests/`, например `tests/accounts/test_profile.py`.

Для Docker используйте команды ниже. Проверки миграций требуют доступной БД; Ruff и pytest — предварительной установки инструментов в проверяемое окружение по согласованию с техлидом. Если инструмент ещё недоступен, явно укажите это в отчёте, не отмечая проверку как пройденную.

```powershell
docker compose run --rm web python -m pip check
docker compose run --rm web python -m ruff check .
docker compose run --rm web python manage.py check
docker compose run --rm web python manage.py makemigrations --check --dry-run
docker compose run --rm web python manage.py migrate --check
docker compose run --rm web python -m pytest tests
git diff --check
```

При работе с локальной `.venv` сначала загрузите переменные `.env` в окружение текущей PowerShell-сессии и запустите контейнер `db`. Установите `DB_HOST=127.0.0.1`, а `DB_PORT` — равным внешнему `POSTGRES_PORT` (по умолчанию `5432`). Затем выполните:

```powershell
.\.venv\Scripts\python.exe -m pip check
.\.venv\Scripts\python.exe -m ruff check .
.\.venv\Scripts\python.exe manage.py check
.\.venv\Scripts\python.exe manage.py makemigrations --check --dry-run
.\.venv\Scripts\python.exe manage.py migrate --check
.\.venv\Scripts\python.exe -m pytest tests
git diff --check
```

Все применимые команды должны завершиться с кодом 0; модели должны соответствовать миграциям, существующие миграции — быть применены. Инициализация Django, создание и удаление отдельной тестовой БД настроены в `tests/conftest.py` через стандартные средства Django. Обычно тестовая БД называется `test_studymate`; пользователь PostgreSQL должен иметь право её создавать. Использовать локальный/CI PostgreSQL, никогда production. Каждый разработчик использует собственную БД. Новые миграции проверять на пустой БД и на предыдущей схеме с тестовыми данными. Отсутствие собранных тестов не подтверждает работоспособность.

### Ручная проверка основного сценария

1. Запустить Django и PostgreSQL по инструкции, применить миграции и при необходимости загрузить демо-данные.
2. Зарегистрироваться, проверить автоматический вход, затем выход и повторный вход.
3. Проверить поиск, направление, роль, открытый набор, сортировку, пустую выдачу и пагинацию каталога. Обновление страницы и Back/Forward должны сохранять условия. Параметры описаны в [контракте каталога](docs/contracts.md#us-04-поиск-и-фильтрация-проектов), дополнительный фильтр роли — в [описании поиска](docs/009-project-search.md).
4. Открыть чужой проект, выбрать свободную роль и подать заявку с необязательным письмом до 300 символов. Увидеть статус «На рассмотрении» в «Моих заявках» и подтвердить запись через admin или ORM.
5. Проверить запрет активного дубля, отклика на собственный проект, закрытую или занятую роль. Убедиться, что другой студент не видит чужие заявки, а запрос без входа или CSRF не создаёт запись.
6. Под руководителем принять заявку и проверить членство и занятость места; отдельную заявку отклонить. Под студентом проверить отзыв заявки на рассмотрении и выход из проекта.
7. Создать проект с ролями и проверить карточку и раздел «Мои проекты», включая ошибки обязательных полей и повтор названия у автора.
8. Обновить страницу и перезапустить контейнеры без удаления volume: данные должны сохраниться.

Для подачи и принятия заявок проверять повторные и одновременные POST, права на каждый объект и отсутствие дублей или переполнения. Тесты блокировок запускать с отдельными соединениями PostgreSQL и реальными транзакциями. Для HTMX проверять полную страницу и фрагмент, сохранение ввода при ошибке, истёкшую сессию, клавиатуру и фокус модального окна, если оно используется.

Отчёт в PR: задача, коммит/ветка, среда, команды, результат Ruff, число pytest-тестов, ручные сценарии и ограничения. Если тесты не добавлены, указать причину. CI и локальная проверка используют одинаковые команды. Один manage.py check или Ruff не подтверждает работоспособность всего проекта.

## Дополнительные инструменты

Разрешены Psycopg, Pillow, Ruff и pytest. Ruff обязателен для проверки каждой фичи и исправления бага; pytest используется для автоматизированных тестов в `tests/`. Версии инструментов и изменения requirements.txt закрепляет техлид. Текущие тесты инициализируют Django без pytest-django. Заголовок HX-Request читается напрямую, django-htmx не используется. Pre-commit и другие новые инструменты согласовываются отдельно. Celery/Redis/Channels нужны только при подтверждённой потребности в очередях или реальном времени. OAuth-библиотеку, production WSGI/ASGI-сервер и хранилище медиа выбирать после уточнения соответствующих требований.
