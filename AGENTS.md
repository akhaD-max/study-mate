# Правила работы над StudyMate

## Область действия и этап

Правила действуют для всего репозитория `study-mate`. Прямые указания владельца задачи имеют приоритет. Сейчас идёт 4-й спринт: подготовлены каркас Django, Docker Compose с PostgreSQL и страницы-заглушки. Цель спринта — работающий локальный сценарий: вход → карточка проекта → выбор роли → подача заявки → просмотр статуса в «Моих заявках». Реализовывать назначенные задачи спринта; описание остальных возможностей в README не расширяет их объём.

Перед работой прочитать этот файл и README целиком, проверить `git status --short`, текущую ветку, diff и более локальные AGENTS.md в затрагиваемых каталогах. Не считать чужие незакоммиченные изменения своей работой.

## Разделение работы и Git

Эти правила предназначены для разработчиков команды и агентов, которых они используют в своих локальных копиях репозитория. Разработчик отвечает за изменения своего агента и их проверку перед PR.

1. До изменений зафиксировать в задаче: цель, критерии приёмки, ответственного разработчика, ветку, список файлов/модулей и зависимости от других задач.
2. Каждую отдельную фичу или исправление бага выполнять в отдельной ветке от актуальной `main`. Использовать формат `feat/XXX-feature_name`, где `XXX` — трёхзначный номер задачи, например `feat/006-registration`. Не смешивать независимые задачи и не коммитить напрямую в основную ветку без прямого поручения владельца задачи.
3. По завершении обязательно подготовить PR в основную ветку с описанием изменений и результатов проверки. Если публикацию выполняет разработчик, передать ему готовые изменения и описание PR. Интеграция — только через PR после ревью; агент не выполняет merge без поручения ответственного разработчика или техлида.
4. Ведение `requirements.txt`, `AGENTS.md` и `README.md` — ответственность техлида. Изменения версий, состава зависимостей, стека, обязательных проверок, команд запуска и правил работы заранее согласовывать с ним. Агент другого разработчика не меняет эти файлы по своей инициативе: передаёт предложение техлиду. Изменения настроек, корневых URL, базового шаблона и Docker/CI-конфигурации согласовывать с ответственным за соответствующую часть проекта.
5. Заранее согласовать имена моделей, сервисов, URL namespaces, шаблонов, контекст и HTMX targets/events. Не создавать две реализации одного сценария в разных приложениях.
6. Моделями и миграциями проекта управляет Денис: он отвечает за схему БД, изменения моделей всех Django-приложений, генерацию и порядок применения миграций. Остальные разработчики передают ему необходимые изменения схемы и согласовывают затрагивающий модели код; не создают параллельные реализации моделей и миграции самостоятельно. Перед генерацией проверить актуальную цепочку и зависимые ветки. Не переписывать применённые/общие миграции, не создавать конкурирующие `0001_initial`.
7. Конфликт миграций разбирать по операциям и зависимостям. Merge-миграция допустима после проверки совместимости. Не склеивать разные схемы механически и не использовать `--fake` для обхода ошибки.
8. Интегрировать небольшими PR в порядке зависимостей. Перед PR обновить свою ветку относительно основной, разрешить конфликты и повторить проверки. Не перезаписывать ветки других разработчиков. Push выполнять в ветку своей задачи в рамках поручения разработчика.
9. Не применять `reset --hard`, `clean -fd`, force push, массовую перезапись файлов или удаление БД/volumes для исправления среды. Не откатывать чужую работу. Разрушительные действия требуют отдельного явного разрешения.
10. Не коммитить `.env`, `.venv`, секреты, дампы, загрузки, локальные логи и кэши. Поддерживать существующие `.gitignore` и `.dockerignore` при добавлении новых локальных файлов.

## Стек и соглашения

- CPython 3.13.16, Django 5.2.17 LTS, PostgreSQL 17.11, HTMX 2.0.11. Python-пакеты фиксируются в requirements.txt; изменения зависимостей и версий согласовывать с техлидом.
- Psycopg binary, Pillow, Ruff и pytest разрешены. Новую прямую библиотеку, фреймворк, сервис или расширение PostgreSQL сначала обсудить с техлидом: задача, встроенная альтернатива, сопровождение, точная версия. Не добавлять автоматически DRF, Celery, Redis, Channels, django-htmx или frontend-сборщик.
- Использовать Django templates, Forms/ModelForms, ORM, auth и sessions. Ruff используется для статической проверки Python-кода, pytest — для автоматизированных тестов. Код — `snake_case`, классы — `PascalCase`, UTF-8, 4 пробела. Интерфейс и документация — по-русски, идентификаторы — по-английски.
- Предлагаемые границы модулей описаны в README. Изменять назначенный модуль; общие изменения согласовывать с его владельцем.
- Многошаговые операции со статусами и местами оформлять явными сервисными функциями. Не прятать критические переходы в сигналы, шаблоны или JavaScript.
- Согласовать кастомного пользователя до первой миграции. Не писать собственное хеширование паролей и хранение session/reset-токенов вместо Django.
- Тестировать на PostgreSQL той же версии, что и разработка. Не подменять его SQLite: ограничения, блокировки и поиск отличаются.

## Проверка и передача

Каждую фичу и исправление бага проверять как минимум командой `python -m ruff check .`. Ruff проверяет код статически и не заменяет проверку поведения: изменённый сценарий также проверить вручную. По возможности добавлять автоматизированные тесты через pytest; для исправления бага предпочтителен регрессионный тест. Если тесты не добавлены, указать причину и выполненную ручную проверку в PR.

Все автоматизированные тесты, общие фикстуры и `conftest.py` хранить в отдельном корневом каталоге `tests/`, при необходимости группируя по модулям. Файлы — `test_*.py`, функции — `test_*`. Не создавать тесты рядом с кодом приложения или в `app/tests.py`.

Использовать команды README. Для изменений приложения выполнять `pip check`, `manage.py check`, `makemigrations --check --dry-run`, `migrate --check`, Ruff и существующие релевантные pytest-тесты; перед интеграцией — весь существующий набор `python -m pytest tests`. Новую миграцию Денис проверяет на пустой БД и переходе с предыдущей схемы на отдельной тестовой БД. Для тестов БД использовать PostgreSQL; транзакционные сценарии проверять отдельными соединениями.

Ruff и pytest пока не включены в командные зависимости; точные версии и конфигурацию их запуска закрепляет техлид. Разрешение использовать инструменты не разрешает самовольно менять requirements.txt. Если инструмент недоступен, явно указать это в результатах проверки. До появления тестов не создавать фиктивные тесты ради успешной команды и не считать отсутствие тестов успешной проверкой.

Для документации достаточно сверки команд, ссылок, версий и `git diff --check`. Не заявлять успешный запуск невыполненных команд и не считать отсутствие собранных тестов проверкой функциональности.

В передаче указать: задачу, ветку и PR, изменённые файлы и поведение, миграции и зависимости, выполненные команды и результаты, невыполненные проверки с причиной, вопросы и владельца следующего шага. При блокере сохранить результат и сообщить конкретную причину; не расширять задачу самовольно.
