## Что хранится в БД

- `Category` — направление (`name`, `slug`); `Project.category` ссылается на него.
- `ProjectRole` — отдельная вакансия конкретного проекта: название, описание, вместимость, флаг `is_open`.
- `ProjectMember` — принятое членство; количество таких записей по роли определяет занятость.
- `Application` — заявка. `pending` не занимает место.

При браузерной проверке существовали направления «Дизайн», «Наука», «Разработка», один открытый проект «StudyMate — проверка командного сценария» и роль `Backend-разработчик` с одним свободным местом. Демо-данные не добавлялись и рабочие записи не менялись.

Общего справочника должностей нет: одинаковое название может повторяться в разных проектах с разными UUID. Поэтому фильтр использует **название**, сравнивает его без учёта регистра, а варианты собирает из реальных `ProjectRole`. `Backend` и `backend` показываются одним пунктом. Синонимы вроде `Backend` и `Backend-разработчик` остаются разными должностями — для их объединения нужен будущий справочник Дениса.

Формата участия в модели проекта нет. В макете оставлен недоступный select «Любой формат» с подписью «Скоро появится». Он не отправляется на сервер и не имитирует фильтрацию. Сложность, навыки и другие отсутствующие поля не добавлялись.

## Как проходит запрос — по файлам

Пример:

```http
GET /projects/?q=чат&direction=development&role=Backend-разработчик&open_only=true&sort=newest
```

1. Существующий `projects:catalog` вызывает `projects.views.catalog(request)`. Исторический `main:catalog` ведёт на тот же путь и обработчик. Главная `/` уже перенаправляла в каталог — новый второй обработчик не создаётся.
2. `CatalogFilterForm(request.GET)` проверяет строки. `strip()` удаляет пробелы по краям; `q` ограничен 200 символами, `role` — 100. Направление проверяется как Unicode slug. Повторы известных параметров дают ошибку, неизвестные параметры игнорируются.
3. `open_only` разбирается строго из `true/false`; при отсутствии параметра используется `true`. Обычный `bool("false")` применять нельзя: это True. Неизвестная сортировка заменяется на `newest`.
4. Только после успешной проверки view передаёт именованные значения в `catalog_projects()`. При ошибках возвращается HTTP 400 с сохранённым вводом, без карточек как результата поиска.
5. В selector поиск строится через ORM: название **или** описание содержит всю строку без учёта регистра; направление, роль и доступность добавляются через **AND**. Подстрока не разбивается на слова, `%` и `_` экранируются ORM как обычный текст.
6. `Exists` проверяет наличие подходящей роли конкретного проекта. При `open_only=true` проект должен быть `open`, а **та же выбранная роль** — открыта и иметь `capacity > Count(memberships)`. Свободная другая роль не компенсирует заполненную выбранную. Если должность не выбрана, достаточно любой доступной роли.
7. При `open_only=false` ограничение набора снимается: можно найти закрытые/завершённые проекты и занятые роли. Права и проверки отклика при этом остаются в прежних сервисах. Фильтр только читает данные.
8. Условия выполняются в PostgreSQL до сортировки и пагинации. `Exists` не размножает проекты по числу ролей. `select_related`, `Prefetch` и аннотация занятости предотвращают запрос на каждую карточку.
9. `Paginator` делит результат по 12. В ссылках сохраняются параметры; при отправке формы поле `page` отсутствует, поэтому новые условия начинают с первой страницы.
10. View передаёт данные в полный `projects/catalog.html` либо `projects/partials/catalog_content.html`. HTMX заменяет `#catalog-content` через `outerHTML` и обновляет URL; восстановление истории получает полную страницу.

На непустой странице гостевого каталога — пять запросов независимо от количества карточек: count, проекты, роли, направления и названия должностей. Пустая выдача может выполнить меньше запросов.

## Интерфейс и авторизация

Figma открыт в браузере. Использована компоновка каталога: компактный синий баннер, поиск и «Создать проект» сверху, блок «Фильтры» слева, счётчик/сортировка и горизонтальные карточки справа. Сохранены существующие рабочие ссылки и меню пользователя. На мобильном экране блоки становятся одной колонкой.

Одна GET-форма охватывает поиск, фильтры и сортировку. «Найти»/«Применить» работают без JS. Две радиокнопки набора отправляют единственное явное значение `true` или `false`, в отличие от сочетания hidden + checkbox с повторяющимся именем. Это небольшое отличие от checkbox макета сохраняет корректную работу обычной формы без JS.

`static/js/catalog.js` содержит делегированные события: смена сортировки отправляет форму, HTTP 400 разрешено вставить как HTML ошибок, сетевой сбой/таймаут/5xx показывает сообщение и повтор с сохранением прежней выдачи. Скрипт не выполняет фильтрацию самостоятельно.

Регистрация и обычный вход ведут через существующую `/` в обновлённый каталог. Для гостя переход в карточку по-прежнему открывает вход с `next=<адрес карточки>`. Проверки чужих заявок и права владельца не менялись.

## Проверки

Среда: CPython 3.13.16, Django 5.2.17, PostgreSQL 17.11. SQLite не использовалась. Рабочая БД сохранена; тесты выполнялись в отдельной тестовой БД.

Успешные команды:

```powershell
git fetch origin --prune
git branch -r --no-merged origin/main
docker compose up -d --build --wait web
docker compose exec -T web python -m pip check
docker compose exec -T web python manage.py check
docker compose exec -T web python manage.py makemigrations --check --dry-run
docker compose exec -T web python manage.py migrate --check
.local/lint/Scripts/python.exe -m ruff check .
docker compose run --rm --no-deps --volume "${PWD}:/app:ro" --volume "${PWD}/.local/test-tools:/test-tools:ro" --env PYTHONPATH=/test-tools web python -m pytest tests -p no:cacheprovider -q
./scripts/local.ps1 test tests.projects.test_search tests.projects.test_catalog --noinput
git diff --check
```

- Полный pytest: **132 passed in 68.33s**. Тестовые инструменты уже находились в игнорируемой `.local/test-tools`, новые зависимости не устанавливались.
- После уточнения явных аргументов selector и нормализованного контекста повторены тесты каталога/поиска: **23/23 OK**.
- Ruff: `All checks passed!`; `pip check`: `No broken requirements found`; Django check без замечаний; изменений моделей нет; все миграции применены.
- В браузере: главная → каталог, фильтр существующей роли, пустой поиск, сохранение параметров в URL, HTTP 400 через HTMX с сохранением текста и фокусом на ошибке, сброс, переход гостя в карточку через login/next; визуальный просмотр на desktop и ширине 390 px.
- Регистрация/вход, переходы к каталогу, доступность выбранной роли, pending, занятые/закрытые роли, все статусы, экранирование, ошибочные/повторные параметры, пагинация и HTMX history проверены автоматизированно.

Первый локальный запуск тестов был заблокирован sandbox-доступом к TCP 5432; повтор с разрешённым доступом прошёл. Первоначальный тест pending использовал устаревшее имя поля `applicant`; исправлен на фактическое `user`. Попытка запуска Linux-пакета Ruff через Windows `.venv` не нашла бинарник; обязательная полная проверка выполнена имеющимся Windows Ruff из `.local/lint`.

Сетевой обрыв, таймаут и HTTP 500 вручную не имитировались. Полного ручного повторения регистрации и подачи заявки в рабочую БД не выполнялось: эти сценарии покрывает полный тестовый набор, чтобы не добавлять лишние рабочие записи.
