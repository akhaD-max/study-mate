# Самостоятельная проверка каталога

Это инструкция для ручной проверки, а не отчёт о её выполнении. Результаты кейсов пока не заполнены. Код исправления проверен отдельным автоматизированным тестом; запуск в браузере остаётся за Владом.

## Подготовка

1. Откройте Docker Desktop и запустите приложение по README. После изменений пересоберите образ:

   ```powershell
   docker compose build
   docker compose up -d --wait db
   docker compose run --rm web python manage.py migrate
   docker compose up -d --wait web
   ```

2. При необходимости загрузите демо-данные командой `seed_demo` из README. Примеры поиска и ожидаемые результаты — в [описании данных](../sprint6/demo-search-data.md). Они не заменяют точные наборы P01–P10 и Q01–Q13 из тест-кейсов.
3. Откройте каталог в Chrome или Edge, нажмите F12, выберите Network, включите Preserve log. Используйте фильтр Fetch/XHR, чтобы видеть HTMX-запросы. Сначала выберите No throttling и убедитесь, что Offline выключен.
4. Запишите коммит (`git rev-parse --short HEAD`), дату, браузер и исполнителя. Если проверяете незакоммиченные изменения, отметьте это отдельно. Порт в примерах ниже — 8000; используйте свой WEB_PORT.

## Проверка исправленного повтора

### Обрыв сети

1. При доступной сети найдите проект по части названия, например `Платформа` для демо-данных. Запомните показанные карточки.
2. В Network выберите Offline.
3. Введите другой запрос, например `Дизайн`, и нажмите «Найти». Дождитесь сообщения об ошибке.
4. Проверьте: предыдущие карточки остаются, есть сообщение «Предыдущая выдача не обновлена» и кнопка «Повторить попытку». Это не пустая выдача.
5. Измените текст в поле на `БЕЗ ОТПРАВКИ`, но не нажимайте Enter или «Найти».
6. Верните No throttling и нажмите «Повторить попытку».
7. Откройте новый запрос `/projects/` в Network → Payload → Query String Parameters. В нём должен быть `q=Дизайн`, а не `БЕЗ ОТПРАВКИ`. Карточки, поле поиска и URL после успеха должны соответствовать повторённому запросу. Сообщение об ошибке должно исчезнуть.
8. Повторите отказ и нажмите повтор ещё при Offline: ошибка должна оставаться, повтор должен быть доступен после завершения запроса. Затем восстановите сеть и повторите успешно.

### Пагинация

Для этого варианта нужны минимум 13 подходящих проектов. Обновлённый `seed_demo` создаёт 13 проектов с доступным набором; используйте пустой поиск и сброшенные фильтры. Если ручные изменения сократили выдачу до 12 проектов или меньше, подготовьте дополнительные данные либо отметьте вариант как заблокированный.

1. Получите выдачу с двумя страницами.
2. Включите Offline и перейдите на страницу 2.
3. После ошибки восстановите сеть и нажмите повтор.
4. Проверьте в Network: повтор содержит `page=2` и прежние фильтры. Отображается вторая страница, URL ей соответствует.

### HTTP 500

Выполняйте только в своём локальном окружении: остановка БД временно затронет все его страницы. Данные и volume удалять не нужно.

1. Убедитесь, что Network работает без Offline и throttling. Откройте каталог с карточками.
2. В PowerShell из корня проекта временно остановите БД:

   ```powershell
   docker compose stop db
   ```

3. Измените поиск и нажмите «Найти». Дождитесь ответа: в Network у запроса каталога должен быть именно статус 500. Если наблюдается другой отказ, запишите его отдельно; он не подтверждает этот вариант.
4. Проверьте сохранение карточек, сообщение об ошибке и кнопку повтора.
5. Восстановите БД и дождитесь готовности:

   ```powershell
   docker compose up -d --wait db
   ```

6. Нажмите повтор. Проверьте сохранённые параметры запроса и обновление каталога. В конце проверки обязательно убедитесь, что БД снова запущена.

### Таймаут

Эта настройка действует только в текущей вкладке. Сервер менять не нужно.

1. При работающей БД и сети загрузите каталог с карточками.
2. В Console сохраните исходный таймаут и задайте короткий:

   ```javascript
   window.catalogPreviousTimeout = htmx.config.timeout;
   htmx.config.timeout = 100;
   ```

3. В Network выберите Slow 3G или другой режим с задержкой больше 100 мс. Не включайте Offline.
4. Измените поиск, нажмите «Найти» и дождитесь таймаута. Проверьте сообщение, сохранение карточек и прекращение индикатора загрузки.
5. Верните No throttling и исходный таймаут:

   ```javascript
   htmx.config.timeout = window.catalogPreviousTimeout;
   delete window.catalogPreviousTimeout;
   ```

6. Нажмите повтор и проверьте успешное выполнение того же запроса. Перезагрузка вкладки также сбрасывает временное изменение таймаута.

## Остальные ручные кейсы

Пройдите [S6-01–S6-09 и регрессию R](catalog-test-cases.md) с указанными там данными и ожидаемыми результатами. Обязательно перепроверьте обычный поиск, смену фильтров, сортировку, пагинацию, сброс, Back/Forward и HTTP 400: после исправления они должны работать как прежде.

S6-10 проверяется тремя видами отказа выше, с фиксацией каждого результата отдельно. Шесть кейсов F полной версии применяются после реализации и согласования соответствующих функций; их отсутствие в текущем демо не означает падение теста.

Для каждого кейса запишите фактическое поведение и статус: «Пройден», «Не пройден» или «Заблокирован» с причиной. Для дефекта сохраните URL, шаги, ожидаемый и фактический результат, HTTP-статус и скриншот без секретов. Итог можно оформить в `docs/sprint-6/qa-report.md`; не отмечайте кейс пройденным только на основании чтения кода.

## Передача исправления

Ответственный: Влад. Рабочая ветка: `main` по разрешению владельца задачи. Описание для PR при переносе в ветку задачи: «Сохранять URL неудачного запроса каталога при повторе».

Изменены JavaScript каталога и его кнопка повтора. Добавлена изолированная pytest-проверка с запуском JavaScript через имеющийся Node.js; без Node.js она пропускается. Новых зависимостей приложения, миграций и изменений серверных операций нет.

Автоматизированная проверка: `python -m pytest --noconftest tests/projects/test_catalog_retry.py -q -p no:cacheprovider`. В ней проверяются повтор после 500/сетевой ошибки/таймаута, сохранение страницы и фильтров при изменённой форме, повторный сбой, очистка после успеха, обработка 400 и игнорирование устаревших ошибок. Это проверка обработчиков на имитации событий, не браузерная приёмка и не полный набор Django-тестов. В обычном полном запуске pytest этот тест также собирается.

На момент передачи изолированная проверка прошла: 1 passed. Ruff, `pip check`, `manage.py check`, `node --check static/js/catalog.js` и `git diff --check` прошли. Проверка цепочки миграций была прервана при недоступной БД; `migrate --check` и полный pytest не выполнены. Docker Engine недоступен, локальный `.env` отсутствует. Ручные кейсы по просьбе владельца задачи не выполнялись и не отмечались пройденными.
