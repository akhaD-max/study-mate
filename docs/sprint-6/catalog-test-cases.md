### S6-09 Ошибочные query параметры

**Приоритет:** высокий. **Способ:** прямой GET к `/projects/`, затем тот же вариант с `HX-Request: true`. Проверять строки независимо.

| Вход | Ожидаемый результат |
| --- | --- |
| `open_only=maybe` | HTTP 400, сообщение об ожидаемых true/false |
| `open_only=` | HTTP 400, пустое значение не трактуется как false |
| `q` длиной 201 символ после `strip()` | HTTP 400, «Введите не более 200 символов» |
| `role` длиной 101 символ | HTTP 400, ошибка длины роли |
| `role=Backend&role=Backend` | HTTP 400, повтор известного параметра запрещён |
| `q=Python&q=Python` | HTTP 400, повтор параметра запрещён даже при одинаковых значениях |
| `direction=bad!slug` | HTTP 400, сообщение о неверном формате направления |
| `direction=unknown-direction-8472` | HTTP 200, пустая выдача, если такого slug нет в справочнике |
| `sort=invalid` | HTTP 200, используется `newest` |

**Ожидается для ошибок:** сохранённый ввод, понятная ошибка, отсутствие успешной пустой выдачи. HTMX отображает ответ валидации; ошибочный HTTP-статус сохраняется. Для корректного `q` длиной ровно 200 символов ошибки длины нет. `%`, `_` и HTML-подобный текст трактуются как пользовательский текст и экранируются, не исполняются.

**Фактический результат:** записать по строкам, включая граничный ввод. **Статус:** Не выполнен.

### S6-10 Ошибки загрузки и повтор

**Приоритет:** высокий. **Предусловие:** каталог уже показывает P01 и P07 по `q=Python`.

**Шаги:** в тестовом окружении поочерёдно воспроизвести HTTP 500, отсутствие сети и таймаут. Каждый раз изменить условие, дождаться отказа, затем восстановить доступность и нажать повтор.

**Ожидается:** при каждом отказе видны сообщение и повтор; предыдущие карточки остаются с обозначением, что результаты не обновились. Сбой не превращается в сообщение «Проекты с такими параметрами не найдены». После восстановления повторяет именно неуспешный запрос с его условиями и обновляет карточки и счётчик. Индикатор загрузки прекращается и при успехе, и при ошибке.

**Фактический результат:** записать отдельно для трёх отказов. **Статус:** Не выполнен.

## 5 Фиксация результатов

Для каждого кейса сохранить: ID, коммит, окружение, дату, исполнителя, фактический результат и статус. Для табличных вариантов записывать результат каждой строки. Кейс получает PASSED только после успешной проверки всех его вариантов; при сбое одного варианта фиксируются FAILED и отдельный баг.

Допустимые статусы: «Не выполнен», «Пройден», «Не пройден», «Заблокирован». Если нет функции или нужных данных, указать блокер. Отсутствие наблюдаемого дефекта без выполнения шагов не считается успешным результатом.

### Шаблон баг репорта

- Название: конкретное неверное поведение.
- Связанный кейс и приоритет.
- Окружение и коммит.
- Предусловия и ID тестовых данных.
- Шаги воспроизведения.
- Ожидаемый результат.
- Фактический результат.
- Скриншот, URL, HTTP-статус и подходящий фрагмент лога без секретов.

Пример названия без утверждения о найденном дефекте: «В открытом наборе отображается проект P05 без доступной роли». Использовать его как реальный баг можно только после воспроизведения.
