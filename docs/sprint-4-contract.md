# Контракт спринта 4 — сценарий отклика

Короткий договор для команды на первый день спринта. Выполнили совместно: Денис (БД), Даня (auth), Влад (бэкенд), Ахад (UI).

## Цель спринта

Связать в один рабочий путь: регистрация/вход → открытие чужого проекта → выбор роли → подача заявки → просмотр статуса «На рассмотрении» в «Мои заявки». Данные сохраняются в PostgreSQL между перезапусками.

## Принятые решения

- **Пользователь:** PK — UUID (`uuid.uuid4`), вход только по `email`. Email нормализуем в lower, уникальность регистронезависимая (UNIQUE LOWER(email)). Логин — стандартным `authenticate` Django.
- **ФИО при регистрации:** на `POST /accounts/register/` требуем только `email` + `password`. Поле `full_name` в модели `accounts.User` есть, но `blank=True` (пустая строка `""` по умолчанию). Заполняется позже в профиле. Так закрываем расхождение Data Dictionary `full_name NOT NULL` и US-01.
- **Системная роль vs роль в проекте:** системная роль — это `is_staff`/`is_superuser` (админ). Роль в проекте — это запись `projects.ProjectRole` + `applications.Membership`. Не смешиваем.
- **Django вместо своих таблиц:** `sessions`, `password_reset_tokens`, `password_hash` не переносим. Используем `django.contrib.auth` (хеш пароля), `django.contrib.sessions` и встроенный `PasswordResetTokenGenerator`. OAuth откладываем.
- **Пароль:** по US-01 минимум 6 символов. В `006` выравниваем `MinimumLengthValidator` с этим. Пока оставляем стандартный 8, но валидацию формы делаем на 6 — расхождение зафиксировали.
- **Занятость мест:** `pending` не занимает место. Занятость = число `Membership` (принятых участников) по конкретной роли. Свободно = `capacity - занятости`.
- **Один активный отклик:** у пользователя максимум одна заявка со статусом `pending` на один проект, независимо от роли. Реализуем `UniqueConstraint` по `(project, applicant)` где `status=pending`.
- **Кто не может откликаться:** автор проекта и уже действующий участник этого проекта (есть активный `Membership`).
- **Открытый набор:** у `ProjectRole` есть явный флаг `is_open: bool` (default True). Если False — отклики не принимаем, даже если места есть. Управление набором — за руководителем, в этом спринте только чтение флага.

## Отложили в backlog

Полный перенос вспомогательных таблиц не делаем: `invitations`, `attachments`, `skill_catalog`, `project_skills`, `comments` (дерево вопросов), `notifications` (суточная сводка), `views/IP-locks`, `OAuth accounts`, полная история статусов проекта (`in_progress/completed` модалки), soft-delete. Перенесем позже отдельными задачами.

## Минимальные HTTP-операции (выбрали HTML + HTMX, без DRF)

Делаем обычные Django `views` + `Forms` + HTML/HTMX-фрагменты. JSON-API не вводим.

| Операция | Метод + URL | Что шлёт | Что возвращает |
|---|---|---|---|
| Список проектов | `GET /projects/` | query `?q=&page=` опционально | HTML страница, список карточек. Для пагинации — HTMX-фрагмент `projects/_list.html`. |
| Карточка проекта + роли | `GET /projects/<uuid:project_id>/` | — | HTML страница с ролями. Каждая роль показывает `capacity`, `occupied`, `is_open`. Кнопка «Откликнуться» только если `request.user.is_authenticated` и роль открыта. |
| Подать заявку | `POST /applications/create/` | `projectRoleId` (UUID, обязательно), `comment` (строка ≤300, необязательно) | Успех: `201` + HTML-фрагмент созданной заявки из БД (`applications/_item.html`) с полями `id`, `project_title`, `role_name`, `status="pending"`, `created_at`. Ошибка: `400`/`403`/`409` + фрагмент формы с ошибками. Требует `CSRF` и вход. |
| Мои заявки | `GET /applications/my/` | — | HTML страница «Мои заявки» (только свои). Доступ только после входа, иначе `302` на `/accounts/login/?next=...` |

Имена полей фиксируем как в таблице. В форме Django поле называем `project_role_id`, но в HTML `name="projectRoleId"` (совместимость с ТЗ Влада). На бэке принимаем оба.

### Форма подачи

```python
class ApplicationForm(forms.Form):
    projectRoleId = forms.UUIDField()
    comment = forms.CharField(max_length=300, required=False, strip=True)
```

Валидация: `comment` ≤300, `projectRoleId` существует, роль принадлежит проекту, `is_open=True`, места есть, нет дубля, не автор, не участник.

### Представление статусов

В этом спринте храним `status` как `CharField(choices)`. Пока используем только:

- `pending` → «На рассмотрении»

Остальные значения зарезервировали для следующих задач: `accepted`, `rejected`, `withdrawn`. В UI показываем бейдж из сохранённой записи, а не из запроса.

### Успешный ответ — из сохранённой записи

После `form.is_valid()` вызываем сервис `create_application(user, role_id, comment)` внутри транзакции. Если успешно — делаем `Application.objects.select_related("project","role").get(pk=new_id)` и рендерим фрагмент. Фронт вставляет его через HTMX (`hx-swap="afterbegin"` в список «Мои заявки» или `hx-redirect` на `/applications/my/`).

### Ошибки

Возвращаем `200` с формой и текстом ошибки, если это валидация, чтобы HTMX заменил форму. Для HTMX-запроса ставим `HX-Retarget` на форму.

| Случай | Код | Сообщение в форме |
|---|---|---|
| Не вошёл | 302/403 | «Войдите, чтобы откликнуться» |
| Нет CSRF | 403 | стандартная страница 403 |
| Роль не найдена / чужая | 404 | «Роль не найдена или набор закрыт» |
| Набор закрыт (`is_open=False`) | 409 | «Набор на эту роль закрыт» |
| Нет мест (`occupied >= capacity`) | 409 | «Мест больше нет» |
| Уже есть активный отклик | 409 | «У вас уже есть заявка на этот проект» |
| Свой проект / уже участник | 403 | «Нельзя откликаться на свой проект» / «Вы уже участник проекта» |
| `comment` >300 | 400 | «Письмо не больше 300 символов» |

Все тексты — по-русски, как в макетах Алисы.

## Что это даёт команде

- Даня делает `accounts` формы по этим полям и правилу `full_name`.
- Влад делает вьюхи и сервис подачи по этому контракту URL/ошибок.
- Ахад верстает страницы и HTMX-фрагменты, зная где взять `status`.
- Денис делает модели и миграции под эти проверки.

Готово, когда каждый может кодить свою часть без уточнений. Это точка синхронизации, а не долгий дизайн.
