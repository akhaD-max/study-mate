# Задача 008: проекты, заявки и соединение HTTP-частей

Дата: 29.10.2026. Ответственный разработчик: Данила. Ветка: `feat/008-project-integration`, создана от `origin/main` (`74b689c`). Публикация PR передаётся разработчику; merge не выполнялся.

## Цель и критерии приёмки

Соединить готовый интерфейс авторизации, формы и сервисы Влада с основным Docker-приложением. Пользователь создаёт проект с ролями, другой пользователь откликается, руководитель принимает или отклоняет заявку, принятый участник видит проект и может выйти. Все изменения работают через обычные HTML-формы с POST и CSRF; HTMX улучшает подачу заявки.

Критерии: основные настройки `config.settings`, доступные URL без демоконфигурации, фиксированный контекст шаблонов, автор и заявитель из сессии, сохранение ввода при ошибках, redirect после успешного обычного POST, HTML-фрагмент при HTMX, защита доступа и последнее место без переполнения.

Зависимости: существующие модели и миграции Дениса, `ProjectCreateForm`, `ProjectRoleFormSet`, `create_project()`, `ApplicationForm`, `submit_application()` Влада, стили каталога и auth-интерфейс. Изменения общих URL/настроек и недостающих небольших частей входят в прямое поручение владельца задачи. С другими разработчиками переписка не велась.

## Как устроено решение

### Настройки и маршрутизация

`config/settings.py`: подключено `applications`, `LOGIN_URL` направлен на `accounts:login`. Секреты, зависимости и настройки PostgreSQL не изменены.

`config/urls.py`: подключены `projects.urls` и `applications.urls`.

Каталог теперь реализован в `projects.views.catalog`. Обёртка, вызывавшая другой обработчик каталога, удалена. `main.views.catalog` — импорт того же callable: старое имя `main:catalog` сохранено как совместимый URL-алиас. Оба имени возвращают `/projects/`; фактически запрос обслуживает один обработчик из `projects`. Два имени необходимы для существующих ссылок, отдельной реализации каталога в main больше нет.

| Метод | URL | Назначение |
| --- | --- | --- |
| GET | `/projects/` | Каталог, фильтры и HTMX списка |
| GET/POST | `/projects/create/` | Создание проекта с formset ролей |
| GET | `/projects/mine/` | Собственные проекты и текущее участие |
| GET | `/projects/<project_id>/` | Карточка, роли, команда, форма отклика |
| GET/POST | `/projects/<project_id>/apply/` | Форма и подача заявки |
| GET | `/applications/` | Собственные заявки |
| GET | `/applications/my/` | Совместимый адрес списка |
| GET | `/projects/<project_id>/applications/` | Входящие заявки, только автор |
| POST | `/applications/<application_id>/accept/` | Принять кандидата |
| POST | `/applications/<application_id>/reject/` | Отклонить кандидата |
| POST | `/applications/<application_id>/withdraw/` | Отозвать свою pending-заявку |
| POST | `/projects/<project_id>/leave/` | Покинуть проект текущему участнику |

Последний URL добавлен для прямо запрошенного сценария выхода: в текущем контракте его не было. Параметр пользователя при выходе не принимается, используется только сессия.

### Создание проекта

`projects.views.create` получает `ProjectCreateForm` и `ProjectRoleFormSet`. Обе формы валидируются, включая management-поля formset. Затем view передаёт очищенные значения в `create_project(author=request.user, ...)`. Автор из POST игнорируется. Сервис атомарно сохраняет проект и роли, обрабатывает ограничение уникального названия автора.

После успеха — redirect на карточку. При ошибке — та же страница с bound-формами и введёнными значениями. Сервисные ошибки привязаны к полям, включая повтор названия. Кнопка добавления роли тоже работает обычным POST и сохраняет ввод, не публикуя проект.

### Карточка и отклик

`detail_context()` возвращает обязательные `project`, `roles`, `form`, `can_apply`, `application_block_reason`. Дополнительно передаются `members`, `is_owner`, `is_member` для интерфейса команды. GET формы отклика использует тот же контекст.

`applications.views.submit` на GET только показывает форму. POST вызывает готовый `submit_application()`; бизнес-правила повторно во view не реализованы. Успех обычного POST перенаправляет в «Мои заявки». Ошибки отображаются с сохранённым письмом; исчезнувшая/закрытая роль не принимается.

HTMX использует `hx-target="#application-form"`, `hx-swap="outerHTML"`. Успех возвращает `partials/sent.html` с сохранённой заявкой и текстом «Заявка отправлена». Ошибка возвращает `partials/form.html` со всеми ошибками. Корневой `id="application-form"` есть в обоих ответах. Заголовки `HX-Retarget` и `HX-Reswap` закрепляют замену; ответы 200 позволяют HTMX показать ошибки без дополнительного JS. GET/ошибки учитывают `Vary: HX-Request`.

`accounts/decorators.py`: `session_required` использует стандартный `login_required`, преобразуя его redirect при истёкшей HTMX-сессии в `HX-Redirect`. Поэтому форма входа открывается целой страницей. CSRF остаётся стандартным Django middleware.

### Приём, отказ, отзыв и выход

Добавлены небольшие сервисы в `applications/services.py`:

- `list_project_applications()` проверяет владельца до выдачи кандидатов.
- `review_application()` блокирует проект, роль, затем заявку в одной транзакции. Проверяет автора, pending-статус, принадлежность роли проекту, доступность места и отсутствие членства. При принятии создаёт `ProjectMember` и переводит заявку в `accepted`; при отказе — только в `rejected`.
- Повтор того же решения безопасен: второе членство не появляется. Изменение уже принятого решения отклоняется сообщением формы.
- `withdraw_application()` разрешает удаление только своей pending-заявки. Это соответствует существующей схеме без `withdrawn` и контракту US-06.
- `leave_project()` получает пользователя из сессии, удаляет его членство и освобождает место. Руководитель покинуть свой проект не может. Повтор выхода безопасен.

Все эти операции блокируют общую строку проекта. У приёма и подачи порядок блокировок совпадает: проект → роль. Это предотвращает одновременный приём двух кандидатов на одно место. Отзыв и выход также сериализуются через проект.

Pending не занимает место. После выхода прежняя заявка остаётся `accepted` как история решения; текущий состав определяется членством. Пользователь может подать новую заявку. Новых статусов, моделей и миграций нет.

### Интерфейс

Созданы рабочие шаблоны карточки, создания, моих проектов, формы отклика, моих и входящих заявок. Общие `templates/workflow.html`, `projects/partials/header.html` и `static/css/workflow.css` используют цвета, шрифты и форму элементов существующего каталога.

В каталоге добавлены ссылки на карточку; в навигации — «Мои проекты», «Мои заявки», «Создать проект». На карточке руководитель видит входящие заявки, участник — выход, кандидат — форму отклика и причину блокировки. Все изменения выполняются HTML-формами с CSRF.

### Тесты и небольшие сопутствующие правки

`tests/conftest.py` теперь по умолчанию использует `config.settings`. С HTTP-тестов сняты `demo_urls`. В `demo_settings.py` убрано повторное подключение приложения: оно уже есть в основной конфигурации.

Добавлен `tests/test_project_workflow.py`: реальная маршрутизация, создание и ошибки formset, автор из сессии, обычная/HTMX-подача, ошибки и приватность, права руководителя, приём/отказ/отзыв/выход, CSRF и вход, конкурентный приём на последнее место через отдельные PostgreSQL-соединения.

В старых auth-тестах исправлены ожидания: main уже перенаправляет с `/` в каталог, email сохраняется в lower. Проверка сессии сохраняется. Моки каталога перенесены на `projects.views`. В существующем middleware убраны три лишних `return None`, выявленные Ruff; поведение не изменено.

Ограничение Docker Ruff: обычный запуск сначала не смог записать кэш в `/app`; для проверки указан `/tmp/ruff-cache`. Затем Linux проверка EXE002 сообщила об исполняемых битах у 68 Python-файлов, скопированных из Windows. Биты в Git — `100644`. Исключено только EXE002 для Linux-проверки, конфигурация линтера и Dockerfile не менялись. Полная локальная команда без исключений проходит. Обычный Docker `ruff check .` поэтому не отмечается как полностью успешный.

Первые полные прогоны обнаружили старые ошибки auth-тестов (ожидание HTML вместо redirect на `/` и поиск email без lower); после описанных исправлений весь набор прошёл. Тесты используют отдельную PostgreSQL БД, рабочие данные в них не участвуют.
