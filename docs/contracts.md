# Контракты StudyMate

Требуемые эндпоинты для US-01–US-12. GET возвращает HTML с указанными данными, POST принимает поля формы; вложенные списки передаются Django formset. `*` — данных пока нет в схеме БД.

Все идентификаторы — UUID. Пользователь берётся из сессии; для POST нужен CSRF. Ошибка формы возвращает форму с введёнными данными и сообщением. Пароли в ответах не возвращаются.

**Sprint 6, 05.11.2026:** актуализирован US-04 по презентации `StadyMate_Sprint6.pptx` (слайды 3–13, 19, 21–23) и текущему коду каталога. Обязательный объём — поиск по названию, фильтр открытого набора, их совместная работа, пустая выдача и ошибки. Принятые HTML/HTMX, UUID и путь `/projects/` сохраняются: JSON и `search`/`status=OPEN` в презентации приведены как примеры. Остальные US описывают общий целевой контракт и не означают, что все функции уже реализованы.

Ниже явно разделены фактическое поведение и целевые изменения Sprint 6. Этот PR меняет документацию; код, OpenAPI и результаты функциональных проверок нужно обновить отдельными задачами. Рекомендации и критерии интеграции находятся после US-04.

## US-01. Регистрация и авторизация

**Эндпоинты:**

- `GET /accounts/register/` — форма регистрации.
- `POST /accounts/register/` — принимает `email: string`, `password: string` (минимум 6 символов); создаёт пользователя, выполняет вход, перенаправляет на `/profile/edit/`.
- `GET /accounts/login/` — форма входа.
- `POST /accounts/login/` — принимает `username: string` (email), `password: string`; перенаправляет на `/projects/`.
- `POST /accounts/logout/` — без полей; завершает сессию, перенаправляет на `/projects/`.

Email уникален без учёта регистра. При неверных реквизитах — «Неверный логин или пароль».

## US-02. Заполнение профиля

**Эндпоинты:**

- `GET /profile/edit/` — возвращает текущие данные профиля для редактирования.
- `POST /profile/edit/` — принимает поля ниже; формат `multipart/form-data`; после сохранения перенаправляет на `/profile/<user_id>/`.
- `GET /profile/<user_id>/` — возвращает публичные данные профиля.

**Поля формы:**

- `full_name: string` — до 150 символов.
- `avatar*: image` — необязательно.
- `university*: string`, `specialty*: string` — обязательно.
- `course*: integer` — 1–6, обязательно.
- `bio*: string` — до 1000 символов.
- `desired_role*: string` — необязательно.
- `skills*: uuid[]` — от 1 до 15 уникальных навыков.
- `interest_tags*: string[]` — без дублей.

**Данные просмотра:** `id`, `full_name`, `avatar_url*`, `university*`, `specialty*`, `course*`, `bio*`, `desired_role*`, `skills*: [{id, name, category}]`, `interest_tags*: [string]`.

## US-03. Проекты студента в профиле

**Эндпоинт:** `GET /profile/<user_id>/projects/`.

**Query:** `tab: active|completed` (по умолчанию `active`), `role: all|leader|member` (по умолчанию `all`).

**Данные карточки:**

- `id`, `title`, `status`.
- `category: {id, name}`, `short_description: string` — до 100 символов.
- `role_in_project: string` — «Руководитель» по `Project.author_id`, иначе `ProjectMember.role.name`.
- `teammates: [{id, full_name, avatar_url*}]` — до 5 человек; `remaining_count: integer`.

Ссылка карточки — `/projects/<project_id>/`. Собственные pending-заявки показываются отдельно от участия; внешнему посетителю доступны только `in_progress` и `completed`.

## US-04. Поиск и фильтрация проектов

### Формат и доступ

**Эндпоинт:** `GET /projects/`, URL name `projects:catalog`. Каталог доступен без входа. Историческое имя `main:catalog` ведёт на тот же путь и обработчик, второй поиск создавать не нужно. Карточка `/projects/<project_id>/` по текущей реализации требует входа.

- Обычный GET возвращает полную страницу `projects/catalog.html`.
- С `HX-Request: true` возвращается `projects/partials/catalog_content.html`, включая корневой `<section id="catalog-content">`, форму, счётчик, карточки, пагинацию или пустое состояние. Замена — `outerHTML`.
- При `HX-History-Restore-Request: true` возвращается полная страница, даже если передан `HX-Request: true`.
- `Content-Type: text/html; charset=utf-8`. `Vary` содержит `HX-Request` и `HX-History-Restore-Request`.
- GET не меняет данные; CSRF для поиска не нужен. Ответ JSON и поля `items`/`recruitmentStatus` не вводятся.

### Query-параметры: целевой контракт Sprint 6

Все параметры необязательные, одиночные. Строки передаются с обычным URL-кодированием UTF-8. В OpenAPI `open_only` имеет тип boolean, в URL используются только литералы `true`/`false`.

| Параметр | Тип и допустимые значения | По умолчанию / правило |
| --- | --- | --- |
| `q` | string, до 200 символов после удаления пробелов по краям | `""`. Поиск подстроки в названии **или** описании, без учёта регистра. Поиск по названию обязателен для Sprint 6; описание сохраняет существующее поведение. Минимум 3 символа отменён: непустая строка ищется от 1 символа. |
| `open_only` | boolean: `true`, `false` | `true` сохраняет привычный вход в каталог открытого набора. `false` отключает ограничение по набору и показывает все существующие проекты независимо от статуса, с остальными условиями запроса. |
| `direction` | string: существующий `Category.slug` либо пустая строка | `""` — все направления. Одно направление; справочник берётся из БД. Неизвестный slug корректного формата даёт пустую выдачу. Формат slug соответствует `Category.slug`: до 100 символов, Unicode-буквы, цифры, `_`, `-`. |
| `sort` | string: `newest`, `oldest`, `members`, `fewer_members` | `newest`. Неизвестное или пустое значение заменяется на `newest`, как в текущем коде. |
| `page` | integer | `1`, размер страницы фиксирован: 12. Нечисловое или пустое значение даёт первую страницу; `0`, отрицательное или число больше последней страницы — последнюю, по существующему `Paginator.get_page()`. |

Повтор одного из известных параметров запрещён: HTTP 400, даже если значения одинаковы. Неизвестные параметры игнорируются и не участвуют в поиске. Неизвестные старые `categories`, `roles`, `difficulty`, а также примерные `search` и `status` не являются алиасами поддерживаемых фильтров. Клиент отправляет только параметры таблицы.

**Правила поиска:** backend удаляет только пробельные символы по краям `q` через `strip()`. `Python`, `python` и ` Python ` эквивалентны. Пустая строка и строка из пробелов отключают текстовый поиск, но сохраняют остальные фильтры. Внутренние пробелы сохраняются; вся строка ищется как одна подстрока, без разбиения на слова. Морфология, опечатки, транслитерация и эквивалентность `е`/`ё` не поддерживаются. `%` и `_` — обычные символы пользовательского текста, не SQL-шаблоны.

Поиск, направление и фильтр набора объединяются через **AND**; название и описание внутри поиска объединяются через **OR**. Сначала фильтруется вся выборка в БД, затем выполняются сортировка и пагинация. Сортировки: `newest` → `-created_at, pk`; `oldest` → `created_at, pk`; `members` → `-member_count, -created_at, pk`; `fewer_members` → `member_count, -created_at, pk`. `member_count` — число записей `ProjectMember`, без отдельного учёта автора, если для него нет членства.

**Что означает «Набор открыт»:** проект имеет `Project.status = open` **и** хотя бы одну роль, у которой одновременно `is_open = true` и `capacity > occupied_places`. Занятость считается по `ProjectMember` этой роли; pending-заявки места не занимают. Полная или закрытая роль не открывает набор. Проект без ролей, с полными/закрытыми ролями или со статусом `in_progress`, `completed`, `cancelled` не попадает в `open_only=true`.

Это вычисляемая доступность набора, а не новое поле/статус БД. Существующие значения `Project.status` и операции US-05/US-12 сохраняются. При `open_only=false` карточка закрытого проекта доступна для просмотра после входа, но возможность отклика по-прежнему определяется US-05. Выдача не гарантирует место: перед POST заявки backend повторно проверяет доступность.

Примеры целевых запросов:

```http
GET /projects/?q=Python&open_only=true
GET /projects/?q=Python&open_only=false
GET /projects/?open_only=true
GET /projects/?q=Python&open_only=true&direction=science&sort=newest&page=2
```

### Ответы и данные шаблона

Это контекст Django templates, а не JSON-схема HTTP-ответа:

| Данные | Значение |
| --- | --- |
| `projects`, `page_obj` | Один объект `Page` с максимум 12 проектами. Номер — `page_obj.number`, число страниц — `page_obj.paginator.num_pages`. |
| `project_count` | Общее число проектов **после всех фильтров, до пагинации**. |
| `categories` | Справочник `Category`: UUID `id`, `name`, `slug`. |
| `search_query`, `selected_direction`, `sort` | Нормализованные `q`, `direction`, выбранная сортировка; используются для восстановления формы. |
| `open_only` | boolean, выбранное состояние фильтра набора; новое поле контекста Sprint 6. |
| `filter_errors` | Словарь ошибок по имени параметра: список строк; при успешной валидации пуст. Новое поле контекста Sprint 6. |

У проекта используются `id` (UUID), `title`, `description`, `status`, `category.{id,name,slug}`, `author` (UUID `id`, имя через `get_full_name()`), `member_count`, `catalog_roles`. `catalog_roles` — открытые по флагу роли, как в текущем Prefetch; каждая содержит `id`, `name`, `capacity`, `occupied_places`, `free_places`, `is_open`. Эта коллекция сама по себе не означает доступность проекта: нужны также статус проекта и свободные места. На закрытом проекте интерфейс показывает «Набор закрыт», даже если у роли осталось `is_open=true`. Авторский аватар и сложность в контракт каталога Sprint 6 не входят.

| HTTP-статус | Ситуация и представление |
| --- | --- |
| `200 OK` | Успешная выдача, в том числе 0 результатов. При нуле `project_count=0`, страница 1 из 1. Сообщение «По вашему запросу проекты не найдены», ссылка сброса и сохранённые условия поиска. |
| `400 Bad Request` | `q` длиннее 200 символов после `strip()`, некорректный формат `direction`, `open_only` вне `true/false` (включая пустое значение), повтор известного параметра. HTML с сохранённым вводом и ошибкой рядом с соответствующим полем. Список не выдаётся как результат такого запроса. |
| `405 Method Not Allowed` | Метод, отличный от GET; обработчик не выполняет поиск и не меняет данные. |
| `500 Internal Server Error` | Непредвиденная ошибка, включая недоступность БД. Страница ошибки для обычного запроса; для HTMX клиент показывает ошибку и кнопку повтора, сохраняя предыдущие карточки. Сбой не превращается в успешную пустую выдачу. |

Пример содержимого ответа 400, `text/html` (структура страницы/фрагмента соответствует заголовкам запроса):

```html
<p role="alert" data-field="open_only">Укажите open_only=true или open_only=false.</p>
```

Для `q` сообщение: «Введите не более 200 символов». Для повторного параметра: «Передайте параметр один раз». Для `direction`: «Некорректный формат направления». Пользовательский ввод экранируется. Сетевая ошибка не имеет HTTP-ответа: интерфейс отдельно сообщает «Не удалось загрузить проекты. Повторите попытку».

### Рекомендации по интеграции frontend и backend

1. Использовать существующую GET-форму в `projects/partials/catalog_content.html`: `q`, `direction`, `sort` плюс `open_only`. Форма должна работать без JavaScript. Если применяется checkbox без `name`, синхронизировать его с единственным именованным полем; надёжнее для обычной формы select/radio с явными `true` и `false`. Отсутствующий checkbox иначе включает default `true`. Не отправлять одновременно hidden и checkbox с одним именем: это нарушит запрет повторов.
2. Оставить `hx-get`, `hx-target="#catalog-content"`, `hx-swap="outerHTML"`, `hx-push-url="true"`. При смене поиска/фильтров/сортировки убирать `page`; при переходе между страницами сохранять все фильтры, в том числе `open_only=false`. Сброс ведёт на `/projects/`: пустой поиск, все направления, `open_only=true`, `sort=newest`, первая страница. Для просмотра всех статусов пользователь явно выбирает `false`.
3. Поиск выполняется по кнопке «Найти»/Enter. Автопоиск не обязателен; при его добавлении использовать задержку ввода и отмену устаревшего запроса, чтобы поздний ответ не перезаписал актуальную выдачу.
4. На время запроса показывать существующий индикатор загрузки. Для HTTP 400 настроить `htmx:beforeSwap` только у каталога: разрешить замену ответом валидации (`shouldSwap=true`), сохранив ошибочный HTTP-статус. Для 5xx, `htmx:sendError` и таймаута сохранять старую выдачу, обозначать её как не обновлённую, выводить сообщение с повтором. HTTP-ошибки обрабатывать через `htmx:responseError`; не превращать все 4xx/5xx в успешную замену. См. [события HTMX](https://htmx.org/events/).
5. Проверить прямой переход по URL, перезагрузку, Back/Forward, запрос без HTMX и восстановление истории. Карточки и счётчик должны совпадать для одной комбинации параметров. GET каталога публичный, а переход в подробности для гостя сохраняет существующий вход через `next`.

### Рекомендации по реализации поиска на backend

Сохранить Django ORM и текущую БД. Отдельный JSON API и новые зависимости для этого сценария не требуются.

1. Добавить отдельную форму валидации query-параметров в `projects/forms.py`. До обычного разбора полей проверить `request.GET.getlist(name)` для запрета повторов. У boolean явно разобрать `true/false`, не применять `bool("false")`. Проверять длину `q` после `strip()`, не обрезать текст молча. Справочник направлений загружается из `Category`.
2. Вынести выборку каталога в `projects/selectors.py`, вызывать её из существующего `catalog`. Валидированные значения передавать именованными аргументами. В шаблоне не выполнять поиск или отбор карточек из уже загруженной страницы.
3. Искать через `Q(title__icontains=q) | Q(description__icontains=q)`. ORM передаёт значения параметрами и экранирует спецсимволы LIKE. Не собирать SQL конкатенацией. Сравнение регистра, включая кириллицу, проверить на целевом PostgreSQL и его collation. См. [QuerySet API Django](https://docs.djangoproject.com/en/5.2/ref/models/querysets/#icontains).
4. Проверять наличие доступной роли через `Exists` с подсчётом членств по **этой же роли**. Нельзя независимо проверять открытую роль и свободную роль: они могут оказаться разными. Ниже фрагмент целевой выборки после валидации, а не уже внесённая реализация:

```python
from django.db.models import Count, Exists, F, OuterRef, Q

available_roles = (
    ProjectRole.objects.filter(project_id=OuterRef("pk"), is_open=True)
    .order_by()
    .annotate(occupied=Count("memberships", distinct=True))
    .filter(capacity__gt=F("occupied"))
)
projects = Project.objects.select_related("category", "author")
if open_only:
    projects = projects.filter(status=Project.Status.OPEN).filter(
        Exists(available_roles)
    )
if q:
    projects = projects.filter(
        Q(title__icontains=q) | Q(description__icontains=q)
    )
if direction:
    projects = projects.filter(category__slug=direction)
```

`Exists` не размножает проекты по числу подходящих ролей. Официальное описание: [Exists subqueries Django](https://docs.djangoproject.com/en/5.2/ref/models/expressions/#exists-subqueries).

5. После фильтрации сохранить `Count("memberships", distinct=True)` для `member_count`, сортировку только через существующий словарь разрешённых значений, Prefetch открытых ролей с `with_occupancy()` и `Paginator(..., 12).get_page(...)`. `select_related`/Prefetch предотвращают отдельный запрос на каждую карточку. Не считать фильтр в Python после пагинации: это исказит количество и страницы. При проверке доступности роли в шаблоне учитывать, что обращение к незагруженному `role.project` может вызвать дополнительный запрос.
6. Для базового поиска изменений схемы не нужно. На большом каталоге сначала измерить запросы и план выполнения на PostgreSQL. Индекс по статусу/дате уже есть; ускорение подстроки отдельными индексами обсуждать с Денисом и техлидом после измерений. Полнотекстовый поиск меняет смысл подстроки и требует отдельного решения.
7. В OpenAPI описать `GET /projects/`, query-таблицу, заголовки HTMX, ответы `200/400/405/500` с `content: text/html`, HTML-примерами и описание контекста отдельно от HTTP-схемы. ## US-05. Подача заявки

**Эндпоинты:**

- `GET /projects/<project_id>/` — возвращает `id`, `title`, `description`, `status`, `category`, `author`, `roles: [{id, name, capacity, occupied_places, free_places, is_open}]`, `can_apply: boolean`.
- `GET /projects/<project_id>/apply/` — форма выбора доступной роли.
- `POST /projects/<project_id>/apply/` — принимает `projectRoleId: uuid` и `comment: string` (необязательно, до 300 символов).

**Результат:** создаётся заявка с `id`, `project_id`, `role_id`, `user_id`, `comment`, `status=pending`, `created_at`. Обычный POST перенаправляет на `/applications/`; HTMX возвращает состояние «Заявка отправлена».

Автор, участник и пользователь с pending-заявкой на проект не могут подать повторный отклик. Роль должна принадлежать проекту, иметь свободные места и открытый набор; проект — `open`. Pending не занимает место.

## US-06. Мои заявки

**Эндпоинты:**

- `GET /applications/` — только собственные заявки, новые сверху.
- `POST /applications/<application_id>/withdraw/` — без полей; удаляет собственную pending-заявку, перенаправляет на `/applications/`.

**Query списка:** `status: all|pending|accepted|rejected`, `q: string` — поиск по названию проекта.

**Данные строки:** `id`, `project: {id, title}`, `role: {id, name}`, `comment`, `created_at` (ДД.ММ.ГГГГ), `status`, `reject_reason*`, `can_withdraw: boolean`.

Статусы: `pending` — «На рассмотрении», `accepted` — «Принята», `rejected` — «Отклонена». Отзыв не меняет занятость: pending место не занимал. Сохранение строки «Проект удалён» требует изменения схемы.

## US-07. Публикация проекта

**Эндпоинты:**

- `GET /projects/create/` — форма, `categories: [{id, name}]`, `skills*: [{id, name}]`.
- `POST /projects/create/` — принимает поля ниже; после сохранения перенаправляет на `/projects/<project_id>/`.

**Поля формы:**

- `title: string` — обязательно, 3–100 символов.
- `description: string` — обязательно, до 5000 символов.
- `category_id: uuid` — обязательно.
- `roles: [{name: string, capacity: integer}]` — минимум одна роль; мест 1–20.
- `difficulty*: string` — необязательно.
- `deadline*: date` — необязательно, не в прошлом.
- `skills*: uuid[]` — обязательные теги компетенций.

Автор назначается из сессии, `status=open`. Автор — руководитель; отдельная запись участника для него не обязательна. Название уникально у автора.

## US-08. Вопросы руководителю

**Эндпоинты:**

- `GET /projects/<project_id>/questions/` — публичный список вопросов и ответов.
- `POST /projects/<project_id>/questions/` — принимает `content*: string`, 15–500 символов.
- `POST /questions/<question_id>/delete/` — без полей; удаляет собственный вопрос без ответа.

**Данные вопроса*:** `id`, `author: {id, full_name, avatar_url}`, `content`, `created_at`, `answer: {id, content, author, created_at, updated_at}|null`, `can_delete: boolean`.

Вопрос задаёт вошедший студент в чужом проекте, максимум 5 вопросов на студента в проекте. После отправки возвращается обновлённый HTML списка. После удаления аккаунта вопрос сохраняется с подписью «Удалённый пользователь».

## US-09. Редактирование проекта

**Эндпоинты:**

- `GET /projects/<project_id>/edit/` — возвращает поля проекта и ролей для редактирования.
- `POST /projects/<project_id>/edit/` — принимает поля US-07, `roles: [{id?, name, capacity, is_open, DELETE?}]`, `stages*: string[]`, `status: open|in_progress`, `updated_at: datetime` для проверки версии.
- `POST /projects/<project_id>/delete/` — без полей; удаление после подтверждения, переход на `/projects/`.

Редактирование и удаление — только автору. Успешное редактирование перенаправляет на `/projects/<project_id>/`.

Нельзя уменьшать места ниже занятости, удалять занятую роль или завершённый проект. Удаление роли удаляет все её заявки после подтверждения. Остальные изменения, включая закрытие набора, сохраняют заявки и их статусы. Несовпадение `updated_at` — ошибка «Карточка была обновлена. Обновите страницу».

## US-10. Входящие заявки и компетенции

**Эндпоинт:** `GET /projects/<project_id>/applications/` — только автору проекта.

**Query:** `sort: match|date_new|date_old`, `role: all|uuid`, `status: all|pending|accepted|rejected`.

**Данные кандидата:**

- `application_id`, `role: {id, name}`, `comment`, `created_at`, `status`, `can_review: boolean`.
- `student: {id, full_name, avatar_url*, university*, specialty*, course*}`.
- `skills*: [{id, name, matched}]`, `missing_skills*: [{id, name}]`, `match_percent*: number`.

Соответствие = совпавшие навыки / требуемые навыки × 100%; пересчитывается при изменении навыков. Письмо длиннее 150 символов сворачивается. Профиль кандидата — `/profile/<user_id>/`.

## US-11. Ответы на вопросы

**Эндпоинты:**

- `GET /projects/<project_id>/questions/manage/` — вопросы руководителю; query `status: all|unanswered|answered`.
- `POST /questions/<question_id>/answer/` — принимает `content*: string`, 3–1000 символов.
- `POST /answers/<answer_id>/edit/` — принимает `content*: string`, 3–1000 символов.
- `POST /answers/<answer_id>/delete/` — без полей; удаляет ответ.

**Данные*:** `questions: [{id, author, content, created_at, answer, status}]`, `unread_count: integer`. Формат `answer` — как в US-08; дополнительно `is_edited: boolean`.

Действия доступны только руководителю. POST возвращает обновлённый HTML вопроса; после удаления ответа статус — «Без ответа». Вопросы и ответы видны публично.

## US-12. Управление командой и набором

**Эндпоинты:**

- `POST /applications/<application_id>/accept/` — без полей; `pending → accepted`, создаёт `ProjectMember` с `project_id`, `role_id`, `user_id` заявки.
- `POST /applications/<application_id>/reject/` — без полей; `pending → rejected`.
- `POST /projects/<project_id>/toggle-enrollment/` — принимает `status: open|in_progress`.
- `POST /projects/<project_id>/roles/<role_id>/toggle-enrollment/` — принимает `is_open: boolean`.
- `POST /projects/<project_id>/members/<user_id>/remove/` — без полей; удаляет членство, освобождает место.

**Результат:** обновлённый HTML заявки/команды с `status`, `members: [{user_id, full_name, role_id, role_name}]`, `roles: [{id, capacity, occupied_places, free_places, is_open}]`.

Действия — только автору. Принятие и создание членства выполняются атомарно с повторной проверкой свободных мест. Закрытие набора блокирует новые отклики и сохраняет статусы прежних заявок. Повторное открытие — `in_progress → open`.

## Чего не хватает в схеме БД

- **US-02, US-03, US-10:** аватар, вуз, специальность, курс, описание профиля, желаемая роль, навыки и теги интересов; справочник навыков и связи с пользователем.
- **US-04, US-07, US-09, US-10:** сложность, дедлайн, этапы проекта и связь требуемых навыков с проектом/ролью. `match_percent` вычисляется, но исходных данных для него нет.
- **US-06, US-10:** причина отказа и сохранение заявок после удаления проекта/пользователя. Сейчас `CASCADE` уничтожает записи; нельзя показать «Проект удалён» или карточку удалённого кандидата.
- **US-08, US-11:** модели вопросов и ответов, даты редактирования, данные о прочтении; сохранение текста после удаления автора.
- **US-05, US-06, US-08–US-12:** постоянные уведомления, получатель, признак прочтения и данные для суточной сводки. При удалении роли уведомляются её заявители; при остальных изменениях — участники и все заявители, без изменения статусов заявок.
- **Целостность заявок:** у `Application` нет ограничения БД, проверяющего принадлежность роли указанному проекту, в отличие от `ProjectMember`.
- **Ограничения:** БД не гарантирует максимум 20 мест, отсутствие переполнения роли, минимум 3 символа в названии, обязательное описание, наличие хотя бы одной роли и запрет удаления завершённого проекта. Эти правила требуют серверных проверок; локальные ограничения полей можно закрепить в БД.

Статуса `withdrawn` нет: отзыв pending можно реализовать удалением заявки. Отдельного общего флага набора нет: текущая схема использует `open/in_progress`, а для конкретной роли — `is_open`.
